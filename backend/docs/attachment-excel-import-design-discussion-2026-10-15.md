# 附件 Excel 导入与结果版本设计讨论稿

日期：2026-10-15。状态：已确认的设计基线；首版代码和本地验证已完成，真实接入待部署验收。

最新调整：Excel 导入定位为开发期辅助入口，不对工作簿或业务链接加密、脱敏，不配置导入密钥，也不要求预配置来源白名单。优先保留统一附件业务结构与共用登记/解析能力，正式 MQ、HTTP 等入口待真实流程确定后适配。

本文保留最初讨论时的源码观察和方案比较，第 1 节为改造前的情况。最终范围、物理模型及实现证据以 [开发任务计划](design-review/attachment-excel-import-implementation-plan.md) 第 6 节及 [运行手册](attachment-excel-import-operations.md) 为准。已完成隔离数据库迁移与本地回归，未联网下载模板内附件或调用真实 OCR/模型。MQ、定时拉取、手动拉取接入器不在本期。已确认 `attachment_id` 在上游稳定且唯一。

## 1. 当前事实

- 模板：`/Users/zhouxy/Downloads/文档解析导入模板.xlsx`，工作表“清单和煤矿常用信息查询”，10 列，100 条附件，全部属于同一煤矿，78 个不同的 `file_name_id`，附件 ID 无重复且存为文本。
- 格式：PDF 53、DWG 29、DOCX 4、DOC 1、XLS 4、XLSX 9。
- `cycle`：季 10、年 41、月 24、周 1、半年 4、空 20。业务已确认 `cycle` 是查询粒度标签，可为日/周/旬/月/季/半年/年；更新型数据可能为空，空值不能自动视为错误。
- `update_rate` 是上报频率编码：1 日、7 周、10 旬、30 月、90 季、180 半年、360 年；0 表示非更新型、上传即报。它与 `cycle` 结合用于后续颗粒度查询，不应直接等同于平台定时任务配置。
- `report_time` 是所属上报周期。`2026/04/00` 中的 `00` 是非日报、非周报、非旬报的月/季/半年/年周期占位表达，不能直接当 SQL DATE，也不能自动改成 1 日。所有链接指向同一个内网 HTTPS 附件服务，是否可达及鉴权未验证。
- `Document` 已保存文件名、对象存储位置、大小、SHA-256、MIME、煤矿 ID/名称、清单类型、上报期、页数、状态、时间。
- `ParseRun` 已有父运行、FULL/INCREMENTAL、规则/模型配置快照、字段数、匹配分、耗时。已有增量提取接口、运行历史接口、规则影响预览。
- `/parse/results` 已按 document_id 选最新创建的一次 ParseRun，不是所有运行全部铺在列表。它依赖解析运行内连接，尚无运行的附件不能自然进入这个结果列表。
- `Batch/BatchItem` 有批次、条目、批次内 client_key 唯一约束、状态、尝试次数、元数据和关联运行。现有批次入口及外部事件入口只接受 legacy 引擎；不能假定直接复用就自动走 reliable v2。
- reliable v2 有不可变 ContentRevision、DocumentProcessingHead、规则/模型冻结、幂等请求、outbox、租约和发布保护。v2 的运行父子关系不等同于已完成用户要求的“补提聚合版本”产品能力。

## 2. 用户目标与设计原则

1. Excel 一行登记一个附件业务条目，系统获得附件并进入解析，不再逐条填写煤矿等属性。
2. 全量保存上游业务属性与原始行，可查询、可追溯、可纠错。
3. 主列表保持一条附件业务记录，按煤矿、清单、周期、文件名筛选；任务队列负责显示执行过程。
4. 增加规则后的补提可形成 5+3=8 的统一结果；每轮执行及每个字段的来源仍保留。
5. 模型变更后显式重提，每次重新提取都分配新的结果版本，旧版本可查看；仅修改平台配置不会悄悄重写历史。
6. 版本是否成为当前版本取决于本轮解析流程是否完整走完，不设置手动发布开关。执行完成、提取到字段、字段可用、匹配分分别表达，匹配分不等于正确率。

## 3. 候选方案

### 方案 A：在 Document 和 ParseRun 上直接扩展

- Document 增加全部业务属性、来源 ID、当前结果指针；ParseRun 增加 result_version、operation_kind。
- 每次初提、补提或全量重提都创建新的结果版本及执行记录，复制或引用父版本中的兼容字段；旧版本保持不可变。
- Excel 复用 Batch/BatchItem，新增校验预览、异步下载与 v2 启动适配。
- 两阶段受理：预览只持久化导入暂存记录；确认后逐行幂等登记，下载落存储后用事务创建解析请求及 outbox。
- 同一稳定 `attachment_id` 同内容重复导入不重提；业务属性冲突进入人工处理；上游内容替换时应产生新的 `attachment_id`，因此新文件按新附件登记，旧附件历史绝不覆盖。
- 改动较小，但默认附件只属于一个清单和周期。后续多关联及原文件替换会让 Document 承担多个身份，迁移风险较高。
- 需增加下载策略和导入权限，沿用结果查看权限；迁移采用可空字段兼容旧记录，不依文件名猜来源 ID。
- 验证导入预览、重复并发、失败恢复、补提汇总、全量切换和历史冻结；通过功能开关关闭新入口并保留新增数据回退，旧入口持续可用。

### 方案 B：明确业务关联、文件内容与结果版本，复用执行底座（后续扩展方向）

- 来源附件身份：来源系统 + 稳定且唯一的 `attachment_id`。上游替换内容时不会沿用旧 ID，因此新内容按新附件身份登记。文件名、链接和 Excel 行号都不是身份键；若未来接入多个来源系统，来源系统仍作为命名空间保留。
- 业务关联：煤矿 + 上游清单 + 上报期 + 来源附件。上游附件可关联多个业务位置，解析结果绑定对应业务关联及规则范围。
- 原文件修订：一个附件可有多个不可变文件修订；每个修订保存源文件 SHA-256、大小、类型、内部对象位置。与现有 ContentRevision 的前处理/OCR/来源修订区分。
- 结果版本 V1/V2：每次初提、补提或全量重提开始时都分配一个新的版本号，并绑定本轮不可变结果快照。版本有 `RUNNING`、`COMPLETED`、`INCOMPLETE`、`FAILED` 等生命周期；只有本轮解析流程完整走完的 `COMPLETED` 版本才自动成为当前版本，未完成或失败版本保留在历史中但不能抢占当前版本。
- “完整走完”遵循可靠执行器的闭合契约：允许字段未找到或待复核，不要求全部字段都可用；字段 `incomplete` 表示搜索/证据流程未闭合，不能切换当前版本。ParseRun 仍负责一次执行；operation_kind 区分初提、补提、全量重提、失败重试，不能只靠 FULL/INCREMENTAL 解释用户意图。
- Excel 统一产出“附件登记请求”，接入服务复用下载、存储、规则解析、启动和 outbox。未来其他接入器仅对接同一登记契约，本期不开发它们。
- **首期边界收窄：一个物理 Document 对应一个执行业务范围（一个上游清单/周期关联）**。原始对象存储和内容缓存可以在未来共享，但当前 `DocumentProcessingHead`、可靠运行和发布保护仍按 document_id 单指针工作，首期不承诺同一 Document 同时承载多个清单/周期的独立当前结果。
- 后续若确认同一来源附件确实可属于多个清单/周期，再选择“每业务关联独立执行 Document、共享 blob”或全面把 head、发布、失效、索引和事实读取改成关联作用域；不能只增加关联表和业务指针。
- 优点是身份、复用、历史及扩展边界清楚；代价是要增加业务关联、结果版本/快照与当前指针，兼容旧列表和事实读取。
- 首期采用增量迁移，不重写 reliable v2 账本、调度器或发布校验。新增业务当前结果指针必须明确与 existing processing head 的职责边界，首期维持一个 Document 一个执行业务范围，禁止形成两套互相矛盾的当前结果。
- 验证和回退同方案 A；首期验证单一执行业务范围下的快照一致性，未来开放多关联前另行验证共享文件与独立结果。通过开关停用新写入口并保留已发布快照读模型，不能直接切回按最新运行读取的旧 SQL。新数据保留，避免破坏性回迁。

| 维度 | 方案 A | 方案 B |
|---|---|---|
| 首期改动 | 较少 | 中等 |
| 一附件多清单/周期 | 需要后续拆分 | 可直接表达 |
| 原文件替换与提取重跑 | 需要谨慎区分 | 边界明确 |
| 与现有模型衔接 | 直接加字段 | 复用执行底座，新增业务读模型 |
| 长期历史与复用 | 更依赖约定 | 由关联与快照约束 |

首期推荐在一个执行业务范围内采用方案 B 的结果快照思想，同时保留方案 A 的单 Document 约束，避免与现有可靠执行底座发生双重当前指针。方案 B 的具体物理表数量尚不确定，不在讨论阶段把概念机械地各建一张表。

## 4. Excel 字段与业务属性

| 模板列 | 暂定含义 | 保存与处理建议 |
|---|---|---|
| mine_code | 上游煤矿编码 | 原样文本保存，内部映射矿井 ID，保留编码命名空间 |
| mine_name | 上游煤矿名称 | 保存名称快照，编码一致但名称冲突预览提示 |
| report_time | 上游所属上报周期；`00` 是非日/周/旬周期的占位 | 原始字符串必留；另存规范周期键，不冒充实际上报时间，不把 `00` 改成 1 日 |
| update_rate | 上报频率编码：0 非更新型，1/7/10/30/90/180/360 分别为日/周/旬/月/季/半年/年 | 原值与规范枚举并存，用于查询颗粒度；不直接驱动平台定时任务 |
| cycle | 查询粒度标签：日/周/旬/月/季/半年/年；更新型可为空 | 原值及规范枚举并存；空值按“未提供标签”保存，不默认月或不定期 |
| file_name_id | 上游清单编号 | 独立保存，映射内部 checklist_type/规则包 |
| file_name | 上游清单名称 | 与附件名称区分，保存原始名称快照 |
| attachment_id | 来源附件 ID | 全程文本，不能用浮点数或按文件名去重 |
| attachment_name | 来源附件名称 | 原样保留，与系统检测类型/内容命名区分 |
| attachment_link | 获取附件的位置 | PDF 下载后保存来源和受控访问记录；Word、Excel、DWG 首期只登记链接，不下载内部副本 |

增加 raw_row、工作表名、Excel 行号、导入批次、模板/映射版本、来源系统、操作者、登记时间和校验结果。可查询和有约束的属性用独立列；上游额外属性保存在扩展 JSON，不能只埋在批次元数据里。真实批次可能达到上万行，预览、校验、确认、后台派发和列表分页不能按 100 行内存表单设计。

上游清单 ID 与内部清单类型分别保存，持久化对应关系、映射版本、确认人。优先编码映射，名称建议仅供人工确认。未匹配不自动执行错误规则，可先登记为“待清单映射”。清单映射完成后再显式启动解析，不必重新导入整份 Excel。映射应支持按上游清单 ID 成组确认和启动，避免导入后重新逐条操作。

周期模型建议保留 report_time_raw、cycle_raw、period_type、period_key、period_start/end（仅确定时填写）、normalization_status。年、半年、季、月、周各有自己的规范键；周起止与跨年规则、半年和季度锚点必须按上游定义确认。业务所属期、实际上报时间、平台接收时间、文件生成/签发时间分开。文档内提取出的日期不能覆盖上游所属期。

## 6. Excel 导入流程

1. 上传 Excel → 表头/文本 ID/重复行/原始日期/必填/格式/清单映射校验。
2. 展示预览：100 条、可解析、待映射、格式暂不支持、业务冲突、重复、无效等。预览阶段不触发附件下载和模型调用。
3. 用户确认有效条目，建立持久化批次与条目。错误可定位工作表及行号，可下载错误清单。有效行独立受理，单行失败不回滚整批。
4. 后台获取附件 → 检验文件签名/大小/格式 → 内部留存原文件 → 确定文件修订 → 冻结规则/配置 → 创建解析任务及 outbox。
5. 批次页分别展示登记、下载、解析进度及失败原因，允许仅重试失败行。不要把“已登记 100 条”显示为“解析完成 100 条”。

所有格式都可以先登记；第一期只对 PDF 下载并启动解析，Word、Excel、DWG 只保存业务属性和来源链接，显示“暂不支持解析”，不下载内部副本。后续扩展格式时，再将对应格式加入下载与解析白名单。这样避免上万行导入时为当前无法处理的文件消耗带宽和存储；这些记录不标为“已留存原文件”，未来获取依赖当时链接可达。若声明为 PDF 的链接实际返回其他格式，按检测结果停止解析并保留类型不符记录。

重复导入优先按来源系统 + `attachment_id` 关联已有附件；已有完整原文件时默认不重复下载，已有兼容解析结果时不重复调用模型，保留每次导入观察。相同 ID 的名称或链接变化只更新来源属性的可追溯修订，不创建新附件。业务归属变化进入冲突处理，不能静默覆盖。

上游内容替换不会沿用原 ID，因此不同 ID 按不同来源附件登记，不能仅因煤矿/清单/文件名相同就推断替换关系。下载后计算源文件 SHA-256：不同 ID、相同内容可共享内部原文件和兼容前处理产物，但保留各自业务属性；字段事实复用还需规则、内容、模型配置、业务范围及授权兼容。模型全量重提的显式请求不被指纹去重吞掉。

同 ID 下载到不同内容是违背上游约定的异常分支。按保留文件修订的兜底原则保存新旧原文件，标记“附件 ID 与内容不一致”，不自动覆盖原文件、切换当前结果或继承旧事实；经核实后再决定处理，正常导入不依赖这条异常路径。批次内及跨批次最终以数据库唯一约束和锁保证幂等。

下载与解析分别重试。每阶段有幂等键和持久化状态；对象存储成功、数据库失败时有暂存标记/清理机制，数据库已提交、派发失败时由 outbox 恢复。取消后旧下载/执行结果不能覆盖新任务。预览与提交之间清单映射或配置变化要提示重新确认或冻结预览版本。

“租约”表示下载任务在一段时间内归某个工作进程处理，该进程通过心跳续期；宕机或长期无心跳后租约到期，其他进程可以接手。“代次”是任务每次重新领取或作废旧尝试时单调递增的执行凭证，与文件版本和结果版本无关。示例：A 持第 1 代下载凭证，失联后 B 持第 2 代接手；A 后来恢复并下载完成，提交时校验凭证已过期，因此不能更新任务、绑定原文件或派发解析。数据库原子校验当前代次、持有人、有效租约和取消状态，下载副本使用尝试独立的暂存键，避免旧进程直接覆盖正式对象。它保证只有当前持有人能提交，不能保证网络动作绝不重复。

下载服务须允许配置指定内网域名/IP/端口（样本即内网 HTTPS），不能简单禁止所有私网。对跳转逐次校验、限制目标和文件大小/超时/并发，鉴权走平台配置，不读取 Excel 里的执行指令或调用任意脚本，也不全局关闭 TLS 校验。待真实下载接入前验证后台服务的网络和证书条件。

## 7. 版本、补提、全量与复用

示例（字段均成功可用时）：

| 动作 | 业务结果 | 执行记录 | 主列表 |
|---|---|---|---|
| 初提 5 个目标 | V1，5 项，流程完整 | R1 | 附件 A 当前 V1，5/5 |
| 规则新增 3 项并补提 | V2，继承 5 项、新提 3 项，流程完成 | R2，关联 R1 | 自动切换为当前 V2，8/8 |
| 显式换模型全量重提 | V3，流程进行中 | R3 | A 当前 V2，显示 V3 重提中 |
| V3 流程完整结束 | V3，8 项，自动定版 | R3 保留 | A 当前 V3，历史包含 V1、V2、V3 |
| V3 执行失败或未完整结束 | V3，失败/未完成版本 | R3 失败或未完成 | A 保留 V2，显示最近 V3 失败/未完成 |

每次重新提取都创建新的结果版本，版本与本轮执行一一对应；补提不原地改写旧版本，而是新运行、新字段修订、新版本快照。历史页顶层按 V1/V2/V3 展示，展开有初提/补提/重试明细和字段来源。重试同一失败任务是否沿用原版本号，需要实现时固定为“同一次操作请求沿用版本号，用户再次发起新的重新提取则新建版本”，避免重复重试产生无法解释的版本空洞。

每个版本必须显式列出每个目标采用哪个字段修订、来自哪个 run/rule/content/model；旧的字段证据与人工复核不能通过新的关联被悄悄改掉。流程完成时自动冻结版本快照、字段统计、匹配分统计口径、元数据与规则/配置快照。历史查看展示当时保存的结果，当前追加的失效/撤回信息另外标明，不把历史内容投影成今天的状态。

新增字段可补提，但补提本身就是新版本；原字段提取语义、单位、维度、证据要求变更，旧字段不能直接继承。第一期将“新增目标补提”与“其他变更重新提取”区分为不同操作类型，但两者都会产生新版本。删除目标后，当前目标数按新版本冻结的目标清单计算，原字段保留历史，不继续计入当前目标。

纯新增补提兼容条件：源文件/内容版本兼容、旧目标语义及模型配置未变、来源事实仍有效且权限允许、复核/失效规则明确。条件不满足，提示全量或受影响目标重提，不能只凭 field_key 或文件 hash 复用。

复用分三层：同内容的原文件存储；兼容前处理/OCR 内容缓存；兼容契约的字段事实。源文件相同不代表跨煤矿/清单/周期可直接复用事实。新业务关联保留自己的权限、业务属性与结果。模型变更“全量重提”必须禁止继承旧事实；是否重做 OCR/前处理按具体配置影响判断。提供“重新提取全部字段”和“重新进行内容处理并提取”两种明确意图，本期可以只开放前者并预留后者。

配置变更默认标识“结果使用旧配置”，由用户显式触发重提；一旦开始重提就创建新版本，不自动修改旧版本。规则发布变化提示“有新增目标可补提”；这是待处理需求，不把旧运行状态改成失败。

结果版本自动定版，不设置手动发布开关：执行完成允许未找到/待复核字段，字段可用性单独表达；字段 `incomplete` 则代表流程没有完整结束。可靠运行 `COMPLETED` 或 `COMPLETED_WITH_REVIEW` 才能自动切为当前附件版本，失败、未完成或取消保留旧当前结果。若旧结果因内容修正或撤销失效，失效标记必须继续生效，不能靠回退变成有效。并发补提与全量重提基于相同父快照做 CAS，首期同业务范围只允许一个改变当前结果的活动任务。

## 8. 文件列表与操作

文件列表以附件业务关联为一行；同一附件关联多个清单或周期时可分业务行，物理文件仍共享。任务列表以 run 为一行。导入批次以导入条目为一行。是否将多关联折叠为一行可在业务确认后设计。

筛选：煤矿编码/名称、上游清单及内部映射、周期类型+所属期或范围、附件名称、来源系统、导入批次、格式、接入状态、解析状态、待补提/旧配置。业务周期和平台创建时间分别筛选。

默认列：附件名/格式/大小、煤矿、清单、所属期、当前结果版本、最新处理状态、字段统计、平均方法匹配分、耗时、首次登记时间、最近结果更新时间、操作。部分可用折叠展示，避免所有详细字段铺成宽表。

统计：目标数、已完成搜索数、有结果数、可用数、待复核数、未找到数、未完成数分别定义。目标是规则提取目标，不是单个表格单元格或每个记录实例。示例“可用 6/8，待复核 1，未找到 1”；不可把 8 个任务完成直接说成提取到 8 个字段。列表当前快照统计包含继承字段，任务页本轮统计只算本次执行目标。

平均方法匹配分保留未经正确率校准的说明，缺失分数展示“—”。跨方法不可直接比较时不合成一个无意义均分；若显示，记录聚合口径/样本数，不把缺失按 0 计算。它也不充当发布条件。

耗时：列表默认最近一次操作耗时，并标“初提/补提/全量”；详情显示当前版本累计执行耗时及下载/排队/前处理/模型阶段耗时。并发任务耗时需分清墙钟时间和累计计算耗时，不混算。

操作：查看当前结果、历史版本、执行记录、补提、重新提取、失败重试（可在更多菜单）。查看区同时展示业务属性、原文件、目标/字段、证据、规则/配置版本、复用来源、复核信息。没有可用结果的附件也能进详情查看登记/获取状态。

## 9. 独立评审后需要补入的约束

- **当前指针必须唯一且按自动定版快照读取。** 现有 `DocumentProcessingHead` 以 `document_id` 为主键，`/parse/results` 按最新创建的运行读取；它不能直接表达“V1 当前、V2 重提中”。首期必须把主列表、查看、导出和事实读取改成已完成版本快照/当前指针，最近任务单独读取。新版本只要流程完整结束就自动切换，未完成或失败版本不能抢占当前版本，不设置手动发布开关。
- **业务快照必须有不可变持久化载体。** `parent_parse_run_id` 和现场事实投影不能冻结版本的字段成员、证据、统计、人工复核及失效水位。流程完整结束时自动冻结版本快照；历史页必须从快照清单读取，不能依赖手动发布动作。当前撤回/失效作为另一个状态展示，不能动态改写历史。
- **补提/全量自动切换必须使用创建时父快照 CAS。** 任务创建时记录 parent snapshot 与版本，流程完整结束时原子比较并自动切换当前版本；同一业务范围首期可以限制一个改变当前结果的活动任务。新增字段才允许继承，字段语义、单位、维度、证据要求、模型配置或来源修订变化必须阻止继承并改走受影响或全量重提。
- **跨批次幂等必须独立于 BatchItem。** 现有批次仅保证批次内 `client_key` 唯一；需要来源系统 + 稳定唯一 `attachment_id` 的身份约束、导入观察记录、文件修订链和独立操作请求 ID。重复登记默认只记录观察并提示旧配置/待补提，不隐式触发重跑。
- **旧入口不能绕过新门禁。** 旧增量、批次重试和人工入口都必须走共享的活动任务互斥、父快照校验和发布服务；“旧数据可兼容查询”不等于“旧写协议可继续修改新附件”。
- **下载需要独立租约与代次。** 同一附件的重试、取消或失联恢复后，旧 worker 即使晚完成，也只能落审计/待清理对象，不能覆盖当前文件修订或重复派发解析；状态需支持心跳、失租回收、大小/超时/并发上限和可重试分类。这是执行控制凭证，不是附件内容版本。
- **权限不能只靠操作 scope。** 若后续需要按煤矿隔离，业务关联必须成为授权入口，统一覆盖导入、列表、历史、原文件/证据、导出和重提。复用可先限于内部物理文件/内容缓存，跨业务事实复用需显式授权。

## 10. 拟议验收场景与影响范围

- 以当前 100 行模板作为夹具，并用更大批次模拟上万行：所有原始列可追溯，非标准日期和空周期不会被静默改值，19 位 ID 精度不丢。
- 预览前后数据库、对象存储和解析任务计数均不增加；混合有效/无效批次只对有效行入队，单行失败不阻止其他行；预览可重启恢复且错误可按工作表/行导出。
- 下载失败只重试该行；服务重启可恢复；重复导入和并发确认不重复建附件/模型任务。
- 同 ID 同内容不重复解析；不同 ID 同内容保留各自来源身份并按兼容性复用；替换后新 ID 按新附件登记；同 ID 不同内容标记异常且不覆盖当前结果。多业务关联留作后续单独设计，不作为首期能力承诺。
- 5+3 补提成功时一条业务附件显示 8 个目标，来源明确；补提部分失败显示真实覆盖，旧快照不变。
- 新增目标补提、旧目标语义/单位/维度变化、模型配置变化、来源文件修订分别走正确的继承/阻止继承/全量路径；并发补提与全量重提按父快照 CAS 只允许一个发布。
- 模型重提不继承旧事实；重提中/失败/未完整结束/自动定版后的列表、详情、历史一致。验证不完整版本不切换当前，旧版本继续可查。
- 使用模板夹具覆盖煤矿、上游清单、日/周/旬/月/季/半年/年及非更新型查询，组合筛选、分页、空结果和统计口径均可核对；列表同时显示“当前结果状态”和“最近任务状态”。
- 旧版本可重现当时的原文件、业务属性、规则、配置、字段、证据、复核与统计，后续修改不会覆盖。
- 被撤回结果不以回退方式重新作为有效事实；旧任务晚到不会抢占新结果。
- 无密钥上传、原始业务属性与链接保存、PDF 下载、导入大小限制和错误导出得到覆盖。

影响模块：Document/ParseRun 等数据模型与迁移、清单映射、统一接入服务、下载后台任务、v2 启动/发布衔接、结果快照及事实读取、结果列表/批次管理/详情历史页、权限与专项验收。最终实现见开发任务计划第 6 节。

旧数据迁移：每个旧 Document 建兼容业务关联；来源 ID 未知保持未知；旧运行按照真实谱系归档，不能仅按创建顺序虚构 V1/V2 或把历史试运行当正式发布；模型快照缺失明确标记未知。旧运行 ID 访问链接保留。
