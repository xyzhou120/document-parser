# v2 文件解析稳定性与性能调整

日期：2026-10-16。范围：当前工作区中的可靠提取 v2，包括初始内容准备、按页提取、模型账本、租约、结果写入与恢复调度。

## 本次调整

| 环节 | 调整 | 目的与边界 |
| --- | --- | --- |
| 来源裁图 | 将有限、正向、与页面有交集的框裁到页面范围；完全越界、倒置、非数值框记为该页失败 | 后续页继续，最终结果保留待核对状态。原文件 hash 错误仍终止运行，不能混同为普通坐标错误 |
| 裁图审计 | 回执保留请求框、实际框、是否裁剪，图像证据保存完整渲染回执 | 来源定位可追溯，不静默改变证据范围 |
| 字段执行 | 外部调用期间通过独立短事务续租，间隔为租约的三分之一且最长 30 秒 | 不在模型调用期间持有数据库锁；暂停、取消、接管后停止旧执行，仍通过 fence 拒绝旧提交 |
| 内容构建 | OCR/视觉兜底期间独立续租；保存检查点时拒绝过期租约 | 防止长 OCR 调用结束后由过期 worker 提交 |
| 依赖故障 | Redis 连接、HTTP 传输、数据库断连等转为持久化 waiting_service，并按 15～300 秒退避 | 连续基础设施异常最多自动重试 6 次，之后 failed_terminal；正常完成一个量子后重置预算，显式恢复重新授予预算 |
| 确定性异常 | 执行器和领域结果 writer 异常写入 failed_terminal | 失败事务先回滚，再用原检查点记录失败，防止重新调度同一异常直至永久 RUNNING |
| 按页协调字段 | 协调字段失败时收敛其他未完成字段；只有协调字段且退避到期才算可执行 | 避免不可领取的兄弟字段使运行永久 RUNNING，或产生持续的空唤醒 |
| 模型账本 | 成功响应先持久化，再更新 Redis 熔断统计；熔断统计失败不阻止保存调用结果 | Redis 短暂中断时仍能复用已付费结果。数据库不可用期间仍无法保证提供方请求恰好一次 |
| 并行页 | 等待并行请求全部返回，分别保留成功结果；失败的预取页留待正式处理 | 不让一页异常丢失其他已完成请求的结果 |
| 执行窗口 | 按页与内容构建使用默认 120 秒、20 个工作单元的窗口，在单元之间移交执行权 | 这是公平调度预算，不是整篇文档时限；正在执行的请求可以超过窗口，由请求超时、心跳和 Celery 上限保护 |
| Celery | v2 唤醒和内容构建启用 late ack、worker lost rejection、3300 秒 soft limit | 唤醒的临时异常显式 retry，重试不携带已消费的 dispatch receipt；仍需 Beat 补偿 |
| 丢失唤醒 | 补偿“已消费消息但尚未领取字段”的空闲运行，以及丢失内容构建消息、worker 退出的构建 | 默认至少空闲 5 分钟再恢复；有活动租约或待派发事件时不重复创建消息 |
| 续投事件 | 运行锁内复用已消费的稳定 continue 事件；sending/pending/outstanding 事件不重复创建 | 避免稳定 dedupe_key 与 `ON CONFLICT DO NOTHING` 组合造成空领取后只等 idle recovery；保留 event_id、attempt 及最近一次接收信息 |
| 调度并发 | 发件箱领取时跳过仍有有效 running lease 的运行 | 避免量子刚开始时 Beat 抢走同一运行的 yield 唤醒；租约交还后由持久事件继续 |
| 预取拆分 | 主请求和预取共用确定性字段拆分规划；旧检查点已有父请求时优先消费父响应 | 新请求不再先发送父单元再拆分，减少无效模型调用；旧已付费请求不删除、不改 dispatch_key |
| 页结果写入 | 逐页候选/证据增量写入；字段摘要每 4 个新单元刷新，完成时强制全量刷新 | 减少每量子加载和重算全部候选；旧结果被修改/移除、规则/来源/覆盖计划变化时立即全量刷新 |
| 原生内容准备 | 原生区域每 4 个批量保存一次；OCR/视觉结果仍立即保存 | 降低大检查点 JSON 的序列化与提交次数；付费结果不会只留在内存 |
| OCR | 一次内容构建内复用 HTTP 连接池并关闭资源 | 保留现有 OCR 并发和 Redis 总容量限制，不直接提高并发 |
| 数据库写入 | 候选和已提取字段按运行批量读取，替代逐字段查询 | 减少数据库往返；仍保留全运行的语义完成度聚合 |
| 证据校验 | 按规则 hash、来源内容、页结果、失败状态、验证器版本缓存候选校验结果 | 未变化页面复用判断；来源、规则、结果变化自动重验。验证语义变化必须升级 PAGE_VALIDATION_CACHE_VERSION |
| 耗时定位 | 量子日志区分 execute_seconds/publish_seconds，模型请求记录 call_id 与耗时 | 支持判断耗时来自外部调用还是发布事务；实际 P95、吞吐及全链路阶段指标仍需实测 |

本次未减少必需证据核验、未跳过未完成范围，也未改变“输出事实与证据，由下游判断业务合格性”的边界。

## 配置与启用

```yaml
agent:
  reliable_wakeup_seconds: 120
  reliable_wakeup_quantums: 20
```

页并发沿用当前配置 `reliable_page_parallelism: 4`。本次新增配置有正数和上限校验，不涉及数据库结构变更；新诊断、缓存与恢复计数保存在已有 JSON 字段。

API、解析 worker 与 Celery Beat 应使用同一套代码。重启后，新领取任务使用新逻辑；正在旧进程中执行的请求不会热更新。不要为切换代码直接清空队列或重置现有解析记录。已经终止或待人工核对的运行不会因部署自动变成成功。

## 旧路径去留建议

建议最终统一到 v2，分阶段停止旧执行入口，同时保留历史结果读取。当前不适合直接删除 ParseService/parse_document_task，现有代码仍存在这些调用方：

- `backend/app/api/integrations.py`：外部接入请求的 engine 只接受 rules/checklist_agent，仍提交旧任务。
- `backend/app/api/batches.py` 与批次服务：部分历史批次重试依赖旧 ParseRun 快照和任务。
- `backend/app/api/parse.py`：旧引擎上传、增量重解析、规则发布包试运行仍可能进入旧任务。
- `backend/app/services/source_revision_service.py`：部分来源订正、强制刷新仍依赖旧内容与运行契约。
- 历史页面产物、结果导出、审核记录和旧运行查询需要保留读取兼容。

建议下线顺序：先迁移外部接入和批次的创建/重试 → 迁移规则试运行、来源订正和重解析 → 停止新建旧引擎任务 → 等待旧队列排空 → 删除旧执行器及专用前处理逻辑。删除前以调用搜索、端到端重解析、结果导出回归验证覆盖情况。

注意 `field_retrieval_v2` 是可靠执行框架内的另一提取策略，不等同于 legacy ParseService。不能因为存在 ReliableFieldExecutor 就把它和旧路径一起删掉；按页执行器仍复用其证据规则与发布保护。

## 验证及限制

本地新增故障注入覆盖：长调用续租、取消后禁止发布、Redis 断连状态化、重试预算耗尽、writer 异常收敛、协调字段失败收敛、无效框单页隔离、已付费响应复用、候选验证缓存失效、内容构建续租、OCR 连接复用以及 retry 不复用已消费投递凭据。

验证记录：

- 最终定向回归：166 passed、3 skipped。包含页拆分/预取、增量写入、内容检查点、恢复调度、模型网关、全局并发和字段完成度。
- 独立临时 PostgreSQL 测试库：13 passed。覆盖实际行锁竞争、连续空领取、稳定续投事件复用、有效租约期间不提前派发、旧 fence/暂停/恢复；结束后测试库已删除，业务库没有修改。
- 全量回归本次快照：820 passed、80 skipped、21 failed。该快照之后补充了本次专用回归用例。
- `git diff --check` 与变更 Python 文件语法编译通过。

建议在 backend 目录运行 `.venv/bin/python -m pytest`，以加载该目录 pyproject.toml 中的 asyncio_mode 配置；从根目录直接运行而不指定配置会使未显式标记的异步测试报“不支持 async 测试”，不能将其判断为解析回归。

相关 PostgreSQL 用例仍要求显式隔离数据库。当前已用临时数据库运行字段调度与可靠执行两组测试；普通本地运行未配置 `P05_TEST_DATABASE_NAME` 时仍会跳过。

全量测试仍发现助手、旧接口 Mock、生成 SQL、来源订正结构检查及真实 Redis 连接相关失败。未为通过测试而绕过现有保护，也未自动覆盖工作区其他功能改动。

目前未完成真实模型/OCR 的端到端故障注入与性能基准。不能将回归测试通过解释为生产验收，也不承诺具体提速倍数。下一步应使用固定的一组原生 PDF、扫描 PDF、表格多页报告和并发附件，比较总耗时、排队时间、模型调用数、token 数、发布事务耗时、恢复次数及结果完整性。

此次没有改变检查点的数据库结构：OCR 结果和汇总刷新仍会涉及累计 JSON；只是减少原生区域的保存频次，并把大部分页量子的候选写入限制在新变化单元。若实测中 OCR 检查点提交或每 4 单元的汇总仍显著耗时，应再将页/区域检查点拆成独立记录，避免直接调整超时或继续提高模型并发来掩盖落库成本。

启用后运行进度仍逐页更新；结果页的字段汇总可能落后最多 3 个新单元，运行结束时强制刷新。暂停期间已提交的新页证据仍在候选账本中，恢复后继续按批次刷新，不会提前把未走完范围判为已完成。没有新数据库迁移要求。模型全局并发继续为 12、请求超时为 180 秒、单篇页并行为 4。
