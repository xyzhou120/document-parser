## 已确认的产品边界

1. 平台面向单个文件提取关键事实，不做跨文件检验、业务公式复算或合格性判断；这些由下游服务依据 Excel 中的检查规则完成。
2. 文件携带所属煤矿和清单类型。平台根据清单类型选择提取规则，持久化单文件结果，并按下游要求交付一个或多个清单的提取结果。
3. 同一清单在多个检查项中出现时，应汇总全部关键字段需求。同一事实应复用字段定义，避免按检查项重复配置。
4. 规则必须能动态增补，以支持新增检查项。规则变更与历史文件补提需要一起设计。
5. 下游不能只看到成功提取的事实而无法区分未找到、未完成或提取失败；具体响应形式待定。
6. 历史文件需要批量补提能力。是否自动触发、触发时机及开关设计待定。
7. 补提应尽可能复用已有解析产物，只执行必要的提取步骤；旧结果及已被下游读取的版本不能被静默覆盖。
8. 下游不负责选择规则或结果版本；平台应提供该文件当前汇总的全部提取信息，并对未提取、未找到、未完成、失败等情况给出状态。版本和批次先作为平台内部管理概念，不作为下游的主要使用负担。

## 从 Excel 提炼出的需求组织方式

- 以“检查项 -> 所需清单 -> 所需原文事实”追踪需求来源，但运行时只按文件所属清单执行提取。
- 第 5 项涉及瓦斯抽采设计、采煤工作面作业规程、瓦斯抽采达标评判报告、钻孔竣工验收台账。平台分别提取每份文件明确记载的设计孔数、实际孔数、补孔记录、施工日期、对象及参数；来源优先级、有效孔数计算和跨文件比较由下游负责。
- 这两份资料约涉及九类文件。官方核定产能、感知数据等外部来源应与单文件提取结果区分，不能由平台根据规则文本补造。
- 规则字段需明确数据语义和粒度，例如设计/实际/计算/实测、工作面/评价单元/测点/单孔/日期，以及单位和原文证据。

## 已核对的平台实现事实

- `Document` 已保存 `mine_id`、`mine_name`、`checklist_type`、`report_period`；上传解析依据清单取规则。
- `ExtractionRule` 支持字段、维度、值类型、提取策略和版本；发布包和运行快照可固定一次运行所用配置。
- 旧增量提取接口 `/api/v1/parse/documents/{document_id}/extract` 会寻找相同文件哈希及前处理版本的 READY 产物，只执行指定字段，并在新 ParseRun 中复制未变字段，保留父运行来源。它不是批量补提调度器。
- 可靠提取 v2 支持指定字段启动运行，并有按字段的执行状态、语义状态、规则哈希、内容修订和请求 ID；尚需核实它与批量补提、旧事实继承和对外结果聚合的完整配合，不能直接宣称整个补提流程已实现。
- 统一事实视图包含事实列表和 `missing_fields`；可靠提取另有字段任务状态。需要设计面向下游的一致字段清单与状态契约，避免空列表的歧义。
- 当前 `/api/v1/parse/results` 按文件返回最新创建的 ParseRun，未限定完成状态；批量补提运行期间需明确稳定可读取版本与进行中版本的选择方式。
- 当前事实 ID 的生成包含 `parse_run_id`。同一事实进入新运行后会有新的事实 ID；跨版本识别及下游引用稳定性不能只依赖该 ID。

## 待讨论的设计问题

1. 对外返回是“事实列表 + 每个配置字段的提取状态清单”，还是每个字段统一返回值与状态？要区分未运行、进行中、失败、完整检索未发现、部分覆盖、有值但待复核。
2. 批量补提的触发方式、选择范围、预估量、审批或开关、失败重试及进度如何设计？规则发布是否只生成待补提计划，由人显式启动？
3. 判断可复用的条件应包含文件哈希、内容修订、前处理版本、字段规则语义哈希、模型/执行配置；哪些变化仅重提字段，哪些必须重新准备内容？
4. 平台内部如何引用或继承旧字段事实并保持幂等？在不要求下游理解版本的前提下，当前汇总结果如何合并并标明状态？
5. 字段清单的业务编辑体验、检查项追溯、试提验证、发布前影响预览如何安排？

## 暂定讨论方向，尚未定案

- 将“字段是否提取到值”和“执行/覆盖是否完整”分开表达；有值也可能证据不足、身份不明或仍有未检索范围。
- 补提创建内部新的运行记录，不修改旧 ParseRun；复用兼容的前处理产物，优先只运行新增或语义改变的字段。最终对外提供文件级当前汇总结果，版本信息主要用于平台追踪与审计。
- 记录补提批次与每份文件的内部运行关系，确保同一请求可安全重试；下游不需要自行判断版本。

## 2026-10-13 用户视图草案，尚未定案

本节是上一轮讨论中的候选视图。用户随后明确：补提方案先待定，下游只取文件当前汇总结果与状态，不应要求其选择规则或结果版本。因此本节涉及“下游显式请求目标版本”的设想不再作为当前设计方向。

### 字段状态视图

- 在单文件结果页按该文件所属清单的冻结规则快照列出全部字段；每行显示字段名、事实数、简要值、所属对象、执行状态、检索覆盖、证据质量、规则版本与来源运行。
- 主状态使用少量面向业务的名称：可交付、有值待核、已检索未发现、部分覆盖、排队/运行中、失败、未纳入当次规则。详细面板保留底层执行状态、语义状态、原因、证据和历史版本。
- 有值不等于可交付；无值不等于已检索未发现。各字段状态应由后端统一投影，不让前端或下游从空数组猜测。
- 规则编辑页可展示样本文档的同一字段状态及提取前后差异；正式文档结果页展示当前稳定版本和进行中的目标版本。

### 补提批次视图

- 入口设在规则发布后的清单级影响分析：目标规则包、变更字段、符合范围的文件数、可复用内容数、需重建内容数、预计任务量和预计成本。先冻结批次目标规则与文件范围，再启动。
- 默认发布规则不自动补提；生成待启动计划。自动触发可作为独立开关，触发时机与范围仍需确认。
- 批次列表显示清单、目标规则版本、文件范围、进度、异常数量、创建人/时间。详情用文件列表展示每份文件的旧稳定结果版本、目标结果版本、待执行字段、可复用阶段和当前状态。
- 批次可暂停、继续、重试失败项和取消未完成项；这些操作不能修改已交付的旧版本。
- 结果按文件完成后独立形成新版本，不等待全批完成。目标版本未准备好时，默认下游读取继续返回旧稳定版本并明确标注其规则版本；显式请求目标版本时，应返回待补提或进行中状态。
- 批次结束允许“完成但有异常”，列出失败、部分覆盖、待核文件。是否将带异常的新版本设为默认读取版本，需要另行确定交付策略；状态必须透明。

## 规则目标类型草案，尚未定案

当前 `ExtractionRule` 以字段为中心，适合“提取一个值”，但 Excel 还包含原文陈述、条目响应和表格结构观察。建议将规则的概念名称提升为“提取目标”，用目标类型区分输出形态；底层仍可兼容现有字段规则。

建议先支持以下五类目标：

1. `value`：数值、日期、名称、参数等单值或多实例事实，保留值、单位、语义类型、对象维度和证据。
2. `statement`：提取一段与目标主题相关的原文陈述，不转成合格/不合格。适合“抽采系统正常、连续运行”的报告描述。
3. `checklist_response`：配置若干条预期条目，逐条提取是否有对应回应、回应原文和证据。适合第 12 项的八条基础条件；`mentioned` 只表示文本提及，不能表示业务满足。
4. `record_collection`：提取重复记录或表格行，例如钻孔竣工验收台账中的孔号、日期、补孔标记和参数；每行独立保留，不强行聚合成一个字段值。
5. `table_observation`：定位目标表格并提取表头、行列、单元格内容和可确认的空白/不可读状态。可以返回空白数量、已检查单元格数量等结构统计，但不输出“大量空白”或合规结论。

这些类型不是五套完全不同的规则编辑器。它们共享清单归属、目标说明、适用范围、维度、证据要求、检索线索和完成状态；只有输出定义和专用配置不同。

### 第 12 项的配置示例

`checklist_response` 可以配置一个目标 `basic_condition_evaluation`，下挂八个条目：每个条目包含条目编号、法规依据、检索词、排除词和期望回应范围。输出只回答：

- 是否找到对应文字描述；
- 找到的原文回应是什么；
- 证据位于哪里；
- 是否因页面未覆盖或内容不可读而无法确认。

平台不判断“是否建立”“是否达到”“是否真实”，也不把报告中的“合格”当作平台判断。

### 表格空白场景的配置示例

`table_observation` 配置表格标题/表头线索和表格范围识别方式。输出表格身份、结构、各单元格的 `filled`、`blank`、`unreadable` 或 `outside_scope` 状态及证据。表格识别失败、OCR 覆盖不完整或合并单元格无法确定时，状态应为 `unknown` 或 `incomplete`，不能直接得出“大量空白”。

### 规则管理结构建议

- 清单：决定文件进入哪套提取目标集合；维护清单说明和适用的文件类型。
- 需求关联：记录 Excel 检查项与清单提取目标之间的多对多关系，供业务追溯和增量补目标；检查项编号不参与单文件提取逻辑。
- 提取目标：稳定 `result_key`、目标类型、名称、语义定义、实例粒度、适用范围、输出数据结构。
- 执行策略：在文件内如何定位、读取和验证目标，包含关键词、章节/表格线索、同义词、排除项、模型指令、完成范围与证据要求。
- 试提样例：每类目标至少保留正例、易混淆反例和未找到/不可读样例，显示预期输出及原文证据，用于配置预览。

业务编辑页面先选择清单和目标类型，再填写“要拿什么、从哪里拿、怎样避免误提、怎样证明找全”，按目标类型展示专用表单；底层实现保留高级配置入口，但不以原始 JSON 作为主要操作方式。

对未来未知场景，不预先发明通用的任意条件表达式。通过可注册的目标类型与执行器扩展，要求每种扩展声明自己的配置校验、输出结构、证据格式、完成状态及试提能力。现有字段规则可作为 `value` 类型逐步迁移。
